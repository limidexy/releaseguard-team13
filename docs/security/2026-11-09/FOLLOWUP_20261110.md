## Docker rollback failure and repair

The first [PR check](https://github.com/limidexy/releaseguard-team13/actions/runs/42651826186) and a second check failed at the existing retained-artifact Governance rollback step. The retained previous image was valid but had no Docker labels. Docker 29 rejected the Go template lookup `.Config.Labels` with `map has no entry for key "Labels"` before image identity could be checked.

`scripts/rollback-target.mjs` now uses `index .Config "Labels"`, which yields `null` when the key is absent. The archive identity and config-digest checks remain in place. A new regression fixture recreates an unlabeled retained image and verifies that proof succeeds without performing any mutations. The targeted rollback suite passed **60/60**, and the full local suite passed **440/440** with no failures or skips.

The updated PR head passed [CI run 42659493342](https://github.com/limidexy/releaseguard-team13/actions/runs/42659493342): both Linux `verify` and `windows-tooling` jobs completed successfully. In Linux, the formerly failing rollback step, dependency advisory gate, image advisory gate and evidence upload all passed. The run's [verification-evidence artifact](https://github.com/limidexy/releaseguard-team13/actions/runs/42659493342) is ID `13694211288`, digest `sha256:6d71fe9242905fc501dfddd784ba42db4cc87d019dedec97540e17cfa8de9d0e`; the tested-image artifact is ID `13694156391`. ## Protected API verification

The [machine-readable API result](followup-evidence/authenticated-api-check.json) records **13 passing checks**. They cover rejection of missing or malformed identity (401), read-only viewer write rejection (403), cross-origin and cross-site mutation rejection (403), permitted same-workspace create/read (201/200), cross-workspace isolation and the gateway CSP header. Rejected writes left no extra application records. This proves those selected local controls with synthetic identities; it does not cover every route, role or production identity provider.

A bounded authenticated **OWASP ZAP 2.17.0 full scan** used a synthetic viewer identity against the protected `/api/v2/applications` route. The scan log confirms a **200 OK** response for that route. The [JSON](followup-evidence/protected-api-zap.json) and [Markdown](followup-evidence/protected-api-zap.md) reports record **0 high, 0 medium, four low alert types and two informational alert types**. The scan exited with code 2 because of low warnings; it was not a clean, warning-free result. The low findings concern Cross-Origin-Embedder-Policy, Cross-Origin-Opener-Policy, Cross-Origin-Resource-Policy and Permissions-Policy headers. They need compatibility review before any change. No access token is retained in these reports.

# ReleaseGuard 云端验收记录

2026 年 10 月 11 日，Team 13 使用 Google Cloud 免费试用实际部署 ReleaseGuard，并调用 Groq Free 的现成模型。以下记录用于组员复现和课堂展示，不代表老师已验收实现或课程全部完成。五人分工与两轮 Sprint 计划保持不变。

## 环境和费用边界

部署地址为 `https://rg-team13.34.21.137.20.sslip.io`。GKE 位于新加坡 `asia-southeast1-a`，两个 `e2-standard-2` 节点，六个应用 Deployment；gateway 为两个副本。PostgreSQL、RabbitMQ、Keycloak 和 HTTPS 入口分别运行；数据库及队列不是公网服务。

外部 HTTPS 证书已实际验证；数据库使用证书校验的 TLS，队列使用 AMQPS。入站网络策略限制服务间访问；出站尚未全面限制。业务数据库分属三个上下文，但共享同一 PostgreSQL 实例；数据库、队列和身份服务都不是高可用部署。

账号仍为免费试用，没有付费升级。控制台在本次检查时显示 S$383.45 和 90 天；账单存在延迟，这不表示本次资源没有消耗。月度预算提醒为 S$40，在 S$10、20、40 时提醒结算管理员/用户；计算试用消耗时不减去促销赠金。提醒不是硬限额。预算定义见 [GCP 官方说明](https://docs.cloud.google.com/billing/docs/how-to/budgets)。

按用户要求，新加坡时间 21:26 云端缩容操作完成，节点组目标为零、无计算实例、无进行中的删除动作。三个持久数据卷仍保留。网站现在暂时不可访问；持久盘、镜像仓库、负载均衡和保留 IP 仍可能消耗试用额度。不得选择付费升级。启动和复验步骤见 [试用环境启停](../deploy/gcp/RUNBOOK.md)。

## 已取得的业务与安全证据

- 云端 API 验收 9/9：未登录拒绝、篡改令牌拒绝、只读账号禁止写入、幂等请求复用同一任务、十用例回放成功、服务身份禁止审核、待审记录保留、非允许来源拒绝、身份管理路径不公开。
- Groq `openai/gpt-oss-20b` 的两个 prompt 各执行十个固定用例，共二十次云端真实调用。原始回答、错误、耗时、可用用量和模型信息均保留。这些是虚构客服政策测试，不是实际客户资料。
- v1 规则分数 20，v2 为 60，两个版本均被门禁阻止。v1 有七个、v2 有四个 provider 级错误，多数与本次 300-token 上限下的截断有关。执行完成不等于回答质量通过；不能把一次比较当成稳定提升，更不能伪造人工评分。
- 三个业务数据库分别执行 `pg_dump`，恢复至当次新建的临时数据库，比对所有 public 表的记录数量及排序后内容哈希，全部一致；临时恢复数据库检查后移除，源数据库保留。本地备份文件在私有目录，不随源码包分发。这是同实例逻辑恢复，不是跨区域灾备、身份库恢复或恢复时间 SLA。

原始证据的源码版本由运行时部署注解读取；实验脚本版本、资源配置变更和最终部署版本必须分别识别。真实模型及早期云端实验使用初始云版本，不应改写为后来 CI 的运行结果。

## 读写与水平扩展

在相同每实例 0.5 CPU、384Mi 限制下，执行两轮配对，顺序为一/三、三/一 Worker。每阶段排除五个预热任务，再测一百个十用例 replay 任务和二百个 GET；共四百个测量任务、二十个预热任务、八百次 GET，错误为零。八个提交客户端及最多八个轮询观察器，结果包含外部客户端延迟。

| 轮次 | Worker | 完成吞吐 jobs/s | 提交 p95 ms | GET p95 ms | 任务完成 p95 ms |
| --- | --- | --- | --- | --- | --- |
| 1 | 1 | 31.85 | 400.37 | 108.54 | 539 |
| 1 | 3 | 31.87 | 434.47 | 166.98 | 480 |
| 2 | 3 | 41.49 | 281.32 | 168.76 | 390 |
| 2 | 1 | 29.04 | 274.74 | 69.93 | 910 |

这些短时结果证明多个 Worker 实际分担任务，但不足以支持线性扩展、持续容量或模型吞吐结论。早期报告的 `medianJobsPerSecond` 对两个样本使用较小值而非两值平均；原始报告保留，修正汇总另存文件，不改变原始观测。修正后的两轮中位数为 30.44 与 36.68 jobs/s，约 1.205 倍，但仅有两轮且离散明显，不能称为稳定提升。全部性能任务为 replay，零模型调用。

KEDA 自动扩容另行测试，不与手动副本对比混淆。第一次积压实验目标达到三副本，但只有两个 Ready，第三个因 CPU 预留不足 Pending；七百任务仍完成。将 Worker CPU request 从 250m 调整为 150m，limit 保持 500m，没有增加云节点。第二次七百任务完成时，新建 HPA 的指标才就绪，因此没有观察到扩容，仍记为未通过。

第三次将“创建新 HPA”和“短时积压”解耦：临时允许零 Worker 并暂停 scale-out，保留 HPA 预热 150 秒，检查实际外部指标，再提交七百 replay 任务、恢复最小一副本并解除限制。外部指标可读取，但 HPA 状态仍在短队列处理完后才更新；七百任务完成，未观察到三副本，仍记未通过。三次原始报告均保留。测试没有手动设置三副本，也没有增加无业务意义的等待来制造漂亮吞吐。

前三次的阶段结论：已经部署实际的队列驱动 scaler，第一次观察到扩容请求和实际一到二副本，但“三个 Ready 副本再自动缩回一个”的完整验收尚未通过。正常流量仍需以一个运行中的 Worker 等待 HPA 的 `ScalingActive=True`，再使用有代表性的持续积压负载，并保留控制器、队列和节点资源时间线；不能用已成功的手动一/三副本测试替代。

随后执行了独立的第四个场景，专门验证故障刺激下的扩缩容控制：保持一台 Worker，等 HPA 实际报告 `ScalingActive=True` 后暂停该 Worker 进程，并同时提交五百个 replay 任务。恢复计时器设为 17 秒；含命令延迟的记录间隔为 18.389 秒，原始报告中“at most 17 seconds”的方法描述过于严格，应按实际 `pauseMs` 解读。没有改延迟指标或添加计算来做性能对比。

此次在新加坡时间 21:19:42 观察到目标三副本，21:19:48 三个全部 Ready，21:20:45 自动缩回一副本；五百任务全部成功，控制闭环通过。任务处理记录仍全部来自原 Worker，说明队列在新增实例参与前已经处理完，不能声称新增实例提升了吞吐或分担了这五百任务。该结果证明故障刺激下的自动扩缩容，不抹掉前三次冷启动/短负载失败，也不替代持续流量实验。

## Git 和 CI/CD

仓库为 [limidexy/releaseguard-team13](https://github.com/limidexy/releaseguard-team13)，补全分支为 `feat/local-course-evidence`，真实草稿 PR 为 [PR 1](https://github.com/limidexy/releaseguard-team13/pull/1)。AI 辅助提交使用明确的作者标记，没有冒充组员。

1. push 前检查编译、十九个单元/适配器/领域测试及基础密钥扫描。
2. GitHub CI 实际安装依赖、构建、跑集成/权限/DDD/故障恢复测试、扫描依赖与镜像，再保存测试过的镜像及源码标识。镜像扫描阻断可修复的 HIGH/CRITICAL 公告，配置为忽略尚无修复版本的公告；通过不能解释成不存在其他漏洞。
3. 手动 CD 只接受本仓库、同一源码 commit 的成功 CI。失败 CI 的部署请求已被拒绝，deploy 没有运行。
4. GitHub 通过短期身份联合授权访问 GCP；不保存云服务账号 JSON 私钥。验证下载镜像的 config digest，发布后验证对应 manifest，再以固定 digest 部署。
5. 依次验证候选镜像、回退旧镜像、再次部署候选镜像。每次均执行真实云端回放 smoke。应用镜像回滚不等于数据库回滚。

第一次实际 CD [38141242613](https://github.com/limidexy/releaseguard-team13/actions/runs/38141242613) 完成候选部署和旧版回退，但再次部署因 Kubernetes 字段管理冲突失败。恢复处理又验证了旧版可用；流水线整体仍记失败。修复仅显式更新六个应用的镜像字段，再执行声明式配置，不强夺其他配置字段。

此次采用用户确认的免费私有仓库方案：有手动触发和版本核对，没有独立人工审批门禁。其他组员的 GitHub 用户名尚未提供；没有真实组员 PR、approval 或合并记录，不将 AI 的 push 当作五人的项目贡献。

修复版实际验收通过：[CI 38142038864](https://github.com/limidexy/releaseguard-team13/actions/runs/38142038864) 与 [CD 38142467085](https://github.com/limidexy/releaseguard-team13/actions/runs/38142467085) 对应同一源码 `dbf6a4be21a978e96510f16837f732b12401d096`。CD 的三个 smoke 阶段全部通过，六个应用最终都运行 manifest digest `sha256:909023689fb5a75b6c7b293b609a79b4bd23c410abd7d6dc2b1ccc96489e092b`，最终就绪副本与期望一致。旧版 digest 为 `sha256:d49d75f32f57d4c7ace5de1059ddf5a4d7e305aab67bfa717b36497e7f6c6632`。GitHub 历史 run 标题仍可能显示 Approved，但该运行的触发方式和证据明确是手动触发，没有独立批准人。
